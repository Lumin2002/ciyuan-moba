# 《次元大作战》2017 战斗核心逻辑分析

针对 `ciyuan_2017`（`com.emagroup.mbzw2.emagroup` v2.16）单一包体的战斗系统专题分析。

**结论先行：这是权威服务器状态同步（authoritative state sync），不是帧同步（lockstep）。**

- 战斗的全部裁定——伤害数值、属性变化、buff/状态、子弹飞行、怪物生成——都在服务端完成，客户端只接收结果并播放表现。
- 客户端保留**本地移动先行**（发送的同时立刻自己走），服务端周期性下发**定长量化坐标**进行校验与校正。
- 客户端原生库里**不存在任何伤害计算函数**；只有攻速、移速、移动方向三类计算。
- 因此：**战斗逻辑无法脱离服务端还原**——但客户端自身携带了完整的协议 schema，服务端接口是可完整还原的。

## 一、判定同步模型的证据链

### 1.1 排除帧同步

对全部 164 个 Lua 文件（105,747 行）与原生库符号做了穷举检索：

| 检索目标 | 结果 |
|---|---|
| `lockstep` / `framesync` / `frame_sync` | **0 命中** |
| `predict` / `interpolat` / `extrapolat` / `rollback` | **0 命中**（`Interpolator` 仅用于动画与飘字） |
| 逻辑帧号 / `framecount` / `seqno` | **0 命中** |

Lua 里出现的 `frame` 全部是两种无关含义：UI 的图片边框（`imgFrame`、`heroframe_*.png`），以及 `JScript_GetGameFrameTime()`——它是**客户端本机毫秒时钟**，用于吟唱延迟与摄像机补间，不是同步帧计数器。

帧同步的必要条件是"所有客户端运行同一份确定性模拟并交换输入指令"。本包既无逻辑帧概念，也无确定性随机与校验和（`checksum`/`crc` 在战斗路径上 0 命中）。

### 1.2 视野（AOI）驱动的实体快照

服务端只把**进入你视野**的实体发给你，这是状态同步的标志性设计（帧同步下所有客户端持有全量实体）：

```
GameDuplicate::OnMsgPlayerEnterMySight(Msg*)
GameDuplicate::OnMsgNPCEnterMySight(Msg*)
GameDuplicate::OnMsgExitMySight(Msg*)
GameDuplicate::onMsgViewSightChanged(Msg*)
GamePlayer::setViewSight(float) / getViewSight()
SExcelMonster::kFFogViewSightFieldNumber     # 每个怪物有独立视野半径
```

对应 Lua `OnMsgPlayerEnterMySight` 收到的是**完整状态快照**，而非增量指令：

```lua
-- logic/gameduplicate_msg.lua:408
local uID,uType,strName,fPosX,fPosY,fDirX,fDirY,fMoveSpeed,fMoveSpeedDebuff,uProfession
    ,uAppearance,uSide,fBaseSpeed,fHp,fHpMax
    , uSkillValueType, uSkillPoint, uSkillPointMax = C_SnapShot_PlayerData(pMsg)
```

序列化侧同样有据：`CSnapShotBaseData` / `CSnapShotMonsterData` / `CSnapShotPlayerData` / `CSnapShotBulletData` / `CSnapShotSingleBuf`，通过 `CDynamicPacket` 的 `operator<<` 落包。

### 1.3 本地移动先行 + 服务端位置校正（决定性）

原生库中存在这些符号：

```
CRoleMoveCtrl::SendAndMove()                          # 发送 且 移动
CMoveCtrl::PushMoveTo(GamePlayer*, Vec3, bool)
CMoveCtrl::TryMoveTo(float, float)
CMoveCtrl::CaluMoveDir(Vec3&)
GameDuplicate::OnMsgMoveList(Msg*)                    # 服务端下发移动列表
GameDuplicate::OnMsgResetMove(Msg*)                   # 服务端重置移动
GameDuplicate::OnMsgPlayerVerifyPos(Msg*)             # 位置校验
GamePlayer::onMsgPlayerVerifyPos(Msg*)
```

反汇编 `GamePlayer::onMsgPlayerVerifyPos`（vaddr `0x2cab88`，188 字节）可以看到它把包里的 **16 位有符号定点坐标**转成浮点后交给移动控制器：

```asm
002cabc4  orr      lr, lr, r4, lsl #8      ; 拼出 int16
002cabd4  sxth     lr, lr                  ; 符号扩展
002cabd8  vcvt.f32.s32 s12, s11            ; 整数 → 浮点
002cac08  vmul.f32 s12, s12, s15           ; 乘固定比例系数（定点还原）
002cac34  bl       _ZN9CMoveCtrl16PushPlayerVerifyEP10GamePlayerN5snake4Vec3Eff
                                           ; CMoveCtrl::PushPlayerVerify(player, Vec3, f, f)
```

`PushPlayerVerify`——把服务端的校验位置**推入**本地移动控制器。这在帧同步里没有存在意义：帧同步的每个客户端跑同一份确定性模拟，位置天然一致，不需要"校验"更不需要"推入校正"。

**坐标用 int16 定点量化传输**本身也是状态同步的特征：帧同步传的是输入指令（按键/方向），状态同步才需要为省带宽而量化位置。

### 1.4 客户端会算什么（以及不会算什么）

穷举客户端原生库中所有 `Calu*` / `Calc*` 符号，涉及战斗的只有三类：

```
Player_CaluAttackSpeed(GamePlayer*, rawSkillLevelInfo&)   # 攻速
Player_CaluAttackSpeedUp(GamePlayer*, rawSkillLevelInfo&)
Player_CaluFinalMoveSpeed(float)                          # 移速
CMoveCtrl::CaluMoveDir(Vec3&) / CMoveCoreCtrl::CaluLength()  # 移动方向与长度
Script_CalcAttackSpeed
```

**没有任何 `CalcDamage` / `CaluHurt` / 伤害结算函数。** 客户端算攻速和移速，是因为它要在本地把角色走起来、把攻击动画放出来；它不算伤害，因为伤害不由它决定。

`Script_GetSkillDamageInfo` 这个符号看起来像伤害计算，但在 Lua 里对它的 5 处引用**全部处于注释状态**（`logic/ui/skilldamagelog.lua` 第 47–51 行），属于遗留未用接口。

## 二、完整战斗回路

### 2.1 上行：客户端发什么

技能释放请求是一个独立的 protobuf 消息 `SSkillPreFire`。字段号由客户端自身恢复（见第五节）：

| # | 字段 | 含义 |
|---:|---|---|
| 1 | `USkillID` | 技能 ID |
| 2 | `USkillLevel` | 技能等级 |
| 4 | `UDirX` | 施法方向 X |
| 5 | `UDirY` | 施法方向 Y |
| 6 | `UTargetID` | 目标 ID（无目标为 `INVALID_CHAR_ID`） |
| 7 | `UChangeDir` | 是否改变朝向 |

Lua 侧入口是 `logic/controller.lua:148`，各操作模式（`drag`、`doubleclick`、`2touch`、`single_touch` 等 15 种）都汇聚到它：

```lua
function GameController:CastSkill( skillid, targetid, targetx, targety, dirx, diry )
    C_CastSkill(targetid,skillid,targetx, targety, dirx, diry)
```

移动/攻击移动走 `C_TryMoveTo(x,y)` 与 `C_AttackToPos(INVALID_CHAR_ID,x,y)`。

**注意：客户端只发"意图"，不发位置结果。** 全部 164 个 Lua 文件里，战斗中通过 `Script_SendMsg` 发出的业务包只有 `msg_deadtime`（报死亡时间）、`msg_gohome`（请求回城）、购买装备、退出战场——移动与技能释放**完全不经过 Lua 消息层**，而是在原生层通过专用战斗连接发出：

```
BattleNetworkInput::SendMsg(Msg*)
BattleNetworkInput::UseBattleConnectSendMsg(Msg*)
```

这是一个**独立于大厅连接的战斗通道**（大厅走 `CJumpSocket`）。另有 `NetDumper::OnSendMsg` 提供收发包转储，可用于验证协议。

### 2.2 下行：服务端发什么

技能结算结果是 `SSkillReply`，字段号同样由客户端自身恢复：

| # | 字段 | 含义 |
|---:|---|---|
| 1 | `USkillID` | 技能 ID |
| 2 | `USkillLevel` | 技能等级 |
| 3 | `UErrorInf` | 失败原因（成功为 0） |
| 4 / 5 | `NSkillPosX` / `NSkillPosY` | 技能落点 |
| 6 | `UFormulaBalanceCounts` | **伤害公式平衡版本号** |
| 7 | `UReplayID` | **回放记录 ID** |
| 8 | `UActionType` | 动作类型 |
| 10 | `UAttackerID` | 施法者 |
| 11 | `VTargetPeople` | 每个受击目标（repeated） |
| 12 / 13 | `NAttackerCurHP` / `NAttackerCurMP` | 施法者当前血/蓝 |
| 14 | `NExtraData` | 扩展数据 |
| 15 / 16 | `NSrcPosX` / `NSrcPosY` | 施法者位置 |

其中 `VTargetPeople` 的每个元素：

| # | 字段 | 含义 |
|---:|---|---|
| 1 | `UPlayerID` | 受击者 |
| 2 | **`NHurt`** | **本次伤害值** |
| 3 | `UEffectFlag` | 效果标记 |
| 4 / 5 | `NAttackPosX` / `Y` | 命中位置 |
| 6 / 7 | `NHitFeedPosX` / `Y` | 受击反馈位置（击退） |
| 8 / 9 | `NCurHP` / `NCurMP` | 受击后血/蓝 |
| 10 | `NFactor` | 系数 |
| 11 | `VPackDamageInfo` | **伤害来源明细**（repeated） |

`VPackDamageInfo` 每个元素为 `{ USkillID, NHurt }`——把一次命中拆成多个来源（技能本体 + 装备 + buff）分别给值。

客户端接到后由 `GamePlayer::onMsgSkillS2cShowDamage(Msg*)` 负责飘字，`CSkillSerializer::LogSkillDamage(...)` 负责战斗日志。**`NHurt` 是服务端算好的一个数字，客户端只负责显示它。**

### 2.3 状态与属性

属性变化同样由服务端下发，客户端被动接收：

```
GameDuplicate::OnMsgAttrChanged(Msg*)
GamePlayer::onMsgCharAttrChange(Msg*)
GamePlayer::OnAttrChanged(void*)
GameDuplicate::onMsgSkillNotifyStatus(Msg*)   # buff/状态通知
GamePlayer::onMsgSkillCut(Msg*)               # 技能被打断
GameDuplicate::onMsgSawSomeOneDead(Msg*)      # 目击死亡
GameDuplicate::onMsgPlayerRelive(Msg*)        # 复活
GameDuplicate::OnMsgTransformHero(Msg*)       # 变身
GameDuplicate::onMsgEquipChanged(Msg*)        # 场内装备变化
```

与之对应，服务端还控制**怪物生成与地图标记**（`onMsgMonsterMapMark`），以及 `onMsgSimpleMonsterPreFire`（怪物起手预警）。技能子弹的位置与朝向也由服务端同步：

```
GameDuplicate::onMsgBulletSyncPos(Msg*)
GameDuplicate::onMsgBulletSyncDir(Msg*)
GameDuplicate::onMsgBulletChangeInfo(Msg*)
```

## 三、C++ / Lua 职责边界

| 层次 | 承担者 | 内容 |
|---|---|---|
| 战斗模拟与裁定 | **服务端**（不在 APK 内） | 伤害公式、命中判定、buff 结算、子弹飞行、AI、怪物生成、胜负 |
| 战斗网络收发 | C++ `BattleNetworkInput` + `CJumpSocket` | 封包、独立战斗连接、`NetDumper` |
| 实体与表现 | C++ `GamePlayer` / `CMoveCtrl` / `CActionQueue` | 本地移动先行、动画队列、受击动作、飘字、音效 |
| 输入与 UI | **Lua**（`logic/controller.lua`、`logic/controltype/*`、`logic/ui/*`） | 把 15 种手势解释成施法意图；技能按钮、CD 显示、血条、小地图 |
| 数值读取 | C++ 解析 protobuf 配置表，经 `JScript_*` / `Script_*` 暴露给 Lua | 技能描述、CD、消耗、图标、攻击距离 |

Lua 在战斗中**只做输入解释与界面表现**。它不参与伤害，不参与位置权威。这也是为什么 `logic/` 下 68 个文件里体量最大的 `gameduplicate.lua`（3709 行）绝大部分是与表现和相机相关的代码，且大段 `C_CastSkill` / `C_TryMoveTo` 调用被注释掉——真正的战斗驱动已经下沉到 C++。

## 四、战斗数值配置与服务端公式的关系

技能数值在 `assets/data/conf/skill_skilllevel_c.dat`（protobuf，108 个字段）。与伤害直接相关的字段：

| # | 字段 | 说明 |
|---:|---|---|
| 20 | **`NFormulaID`** | 伤害公式 ID |
| 21 | **`NGodFormulaID`** | 特殊/无敌公式 ID |
| 28 | `NTargetHurtActRate` | 受击动作概率 |
| 54 / 55 / 81 | `NDamageCoefficientFirst` / `...Second` / `...S` | 伤害系数 |
| 82 | `NDamageType` | 伤害类型（物理/魔法/真实） |
| 8 / 9 / 10 | `FRange` / `FSpeed` / `NFlyTime` | 弹道范围、速度、飞行时间 |
| 20 | `NFormulaID` | —— |
| 70 / 74 / 75 | `NDuration` / `NSkillShakeTime` / `NSkillDuration` | 持续与震屏 |
| 76 | `StrScript` | 技能脚本名 |

关键点：**技能表里没有伤害公式本身，只有公式 ID 与系数。** 公式按 `NFormulaID` 索引，实现在服务端。`SSkillReply.UFormulaBalanceCounts` 进一步说明公式是**带版本号**的——同一个 `NFormulaID` 在不同平衡版本下可以算出不同结果，客户端把版本号记录下来以便与回放/战报对齐。

因此：**客户端配置表给出的是公式的输入与参数，不是公式。** 想还原战斗数值必须重写公式实现，而公式本体不在 APK 中。

其余相关表：`SSkill_Skillbase`（34 字段，含 `BIsClientStart`、`NCombineDamage`、`NAutoSearchType`、`NBindStatus`）、`SSkill_StatusList`（58 字段，buff/状态，含 `NAttrChangeFactor`、`StrImmuneAttribute`）、`SSkill_NegativeMe`（23 种失败原因）、`SSkill_NegativeOther`（24 种目标条件）、`SBullet`（子弹定义）。

`SSkill_NegativeMe` / `NegativeOther` 的存在说明客户端**知道全部施法失败原因**，可以本地预判并置灰按钮/提示"魔法不足"，但真正的裁定仍以服务端返回的 `UErrorInf` 为准。

## 五、客户端自带的完整协议 schema

`libgame.so` 里编译进了 **1263 个 `k*FieldNumber` 常量**，覆盖 **142 个消息**。protobuf 为每个字段生成 `static const int kFooFieldNumber = N;`，这些常量的**值就是字段号**，所以客户端二进制本身就是一份完整 schema 文档——**包括那些从未发布 `.proto` 的表与全部网络消息**。

`inspect_proto_schema.py` 从符号表恢复这些值（映射 vaddr → 文件偏移后读 4 字节小端）。

### 5.1 与 2018 包 `.proto` 的交叉验证

2018 包是唯一附带 `.proto` 的版本（50 个文件）。用 2017 客户端恢复出的字段号去对：

| 结果 | 数量 |
|---|---:|
| 共有消息 | 76 |
| 字段号**完全一致** | **815** |
| 字段号**冲突**（同名不同号） | **22** |
| 仅 2017 客户端存在 | 68 |

815 个字段号在相隔一年的两个版本间完全一致，验证了恢复方法的正确性；而 22 个冲突则是**真实的版本间字段重排**：

| 消息 | 字段 | 2017 | 2018 |
|---|---|---:|---:|
| `SItem_Item` | `strItemName` | 23 | **2** |
| `SItem_Item` | `strIconFile` | 26 | **3** |
| `SItem_Item` | `nGold` | 6 | **4** |
| `SItem_Item` | `nDiamond` | 7 | **5** |
| `SItem_Item` | `nPoint` | 46 | **6** |
| `SItem_Item` | `nSell` | 48 | **7** |
| `SItem_Item` | `nAthPoint` | 49 | **8** |
| `SItem_Item` | `nItemType` | 44 | **9** |
| `SItem_Item` | `nColdDownTime` | 22 | **10** |
| `SItem_Item` | `strScript` | 47 | **11** |
| `SHeroSkin` | `nSkinLevel` | 15 | **12** |
| `SHeroSkin` | `sChangeMonsterID` | 13 | **23** |
| `SVIPGroup` | `strBagID1..4` | 2–5 | **3–6** |

**实践含义（重要）**：整张 `SItem_Item` 表在 2018 被重新编号。若直接用 2018 的 `.proto` 去解析 2017 的 `item_item_c.dat`，会把字段名与数值**系统性错配**——`strItemName` 会被读成 2018 的 2 号字段，得到完全错误的结果，而且不会报错。**解析 2017 配置表必须使用 2017 客户端自身的字段号**，即 `proto_schema_recovered.json`。

### 5.2 网络消息家族

恢复出的消息里包含登录与鉴权协议，前缀即角色：

- `Sc2g*` / `Sg2c*`：client ↔ game（游戏服），如 `Sc2gReqClientLogin`、`Sg2cAckClientLogin`、**`Sg2cSecretKey`**（进战斗的密钥交换）
- `Sa2g*` / `Sg2a*`：a ↔ game，如 `Sa2gReqExchange`、`Sa2gReqSendItem`、`Sg2aAckSendItem`、`Sa2gReqSendStatusHero`、`Sa2gReqSendAtrrItemExchange`、`Sg2aUserLogout`
- 另有 `Sg2cErrorInfo` / `Sa2gErrorInfo`

这与 Lua 层 `msgdef.lua` 的 `C2S/S2C`、`C2M/M2C`、`C2G/G2C`、`CMS/SMC` 分层一致：至少存在**大厅服、匹配服、游戏服、商城服**四类后端。

## 六、断线重连与回放

重连机制的存在本身也指向权威服务端：

```
MSG_C2S_DEAD_INFO = 1500                  -- 断线重连进场请求死亡信息
MSG_C2S_REQ_TIME  = 1498 / MSG_S2C_SYNC_TIME = 1499   -- 客户端时间与服务器同步
MSG_S2C_NOTIFY_TIME = 23458               -- 服务端下发战场时间
MSG_S2C_START = 23475                     -- 由服务端宣布开战
MSG_S2C_ALL_PLAYER_MAP_LOADED = 23512     -- 服务端协调全员地图加载完毕
MSG_S2C_NOTIFY_BIND_AI / DISBIND_AI = 23517/23518  -- 服务端把 AI 绑定到挂机玩家
```

Lua 侧 `gamelobby.lua` 的 `Reconnection()` 设置 `g_bReconnection` / `g_batReconnection`，`GameDuplicate` 的广播类型含 `BatInfoType_ReConnect = 24`。

`MSG_C2S_REQ_TIME` / `MSG_S2C_SYNC_TIME` 的存在说明客户端会与服务端**对时**——这是状态同步中在两次快照之间做平滑插值所必需的，帧同步不需要对时。

**回放**：`SSkillReply` 带 `UReplayID`，且广播系统有 `GameDuplicate::ParseBroadCast`。服务端逐条记录技能结算结果，因此理论上**存在一份包含权威结果的战斗数据流**。这为"离线复现一场战斗的表现"提供了可能——但那是**播放已裁定好的结果**，不是重新模拟战斗。

## 七、"能否脱离服务端还原战斗"

分三层回答：

| 层次 | 能否还原 | 依据 |
|---|---|---|
| **协议与接口** | ✅ 可完整还原 | 客户端自带 1263 个字段号 / 142 个消息；`SSkillPreFire` 上行、`SSkillReply` 下行结构清晰 |
| **数值配置** | ✅ 可完整还原 | 配置表用 2017 自身字段号即可正确解析（注意不可用 2018 的 `.proto`） |
| **权威战斗模拟** | ❌ 无法还原 | 伤害公式只有 ID（`NFormulaID`）与系数，公式本体在服务端；客户端无任何伤害计算函数 |

结论：**客户端提供了一份完整的"战斗协议说明书"和全部输入参数，但没有提供计算规则。** 要在无服务端的情况下跑起战斗，必须自行实现一个服务端，其中包括根据 `NFormulaID` 与系数重建伤害公式——而这部分需要靠可见的战斗结果反推，无法直接读取。

最能说明问题的一点：客户端连自己的位置都不完全信任（`PushPlayerVerify` 校正），却从不计算自己造成了多少伤害。
