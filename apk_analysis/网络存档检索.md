# 网络存档检索：archive.org 可用（需走系统代理）

调查"能否连接互联网档案馆"的结果，以及检索到的内容。

> **重要更正**：本文早期版本结论为"archive.org 被网络层封锁、不可达"。**该结论是错的。**
> 真实原因与解决办法见第一节。archive.org 在本机完全可用，之前失败只是因为**我的
> shell 没有使用系统代理**。

---

## 一、失败的真实原因：shell 未使用系统代理

### 1.1 现象与误判

`web_fetch` 与 pwsh 的 `curl` 访问 archive.org 全部失败（`TypeError: fetch failed` / 连接超时），
而 `example.com`、`api.github.com`、`index.commoncrawl.org` 都正常。据此我曾误判为
"DNS 污染 + IP 层阻断"。

当时观察到的现象**确实**符合封锁特征：

| 解析器 | `archive.org` 解析结果 |
|---|---|
| 系统默认 | `2a03:2880:...face:b00c:...`（Facebook IPv6 段）、`88.191.249.182` |
| `223.5.5.5` | `69.63.181.12`（Facebook IPv4） |
| `8.8.8.8` | `103.42.176.244` |
| `1.1.1.1` | 解析失败 |

直连 archive.org 真实 IP 段（207.241.x.x）也超时/重置。

### 1.2 实际原因

由用户提示"我的谷歌浏览器可以访问 archive.org"后排查发现：

```
HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings
    ProxyEnable  : 1
    ProxyServer  : http://127.0.0.1:12334     ← 系统代理（Chrome 走它）
netsh winhttp show proxy  →  Direct access (no proxy server)
环境变量 HTTP_PROXY / HTTPS_PROXY  →  空
```

**结论**：本机运行着本地代理（`127.0.0.1:12334`），Chrome 走系统代理因此能访问；
而 `curl` **不读取 Windows 注册表的 WinINET 代理设置**，环境变量又是空的，所以直连被墙。
`archive.org` 的 DNS 污染与 IP 阻断是真实存在的，但**只需走代理即可绕开**。

### 1.3 解决办法

给 curl 显式指定代理即可，archive.org 立即恢复：

```bash
curl --proxy http://127.0.0.1:12334 "https://web.archive.org/"
# → 200

curl --proxy http://127.0.0.1:12334 \
  "https://archive.org/wayback/available?url=emagroup.cn"
# → {"archived_snapshots":{"closest":{"status":"200","available":true,
#      "url":"http://web.archive.org/web/20220501213316/http://www.emagroup.cn/"}}}
```

> 注：本环境不具备修改 shell 级代理的能力（不使用需审批的提权），因此**后续所有联网检索
> 都需显式带上 `--proxy http://127.0.0.1:12334`**。若该代理未运行，则 archive.org 不可达。

## 三、这条线索的价值：可能拿到缺失的 `.s` 脚本

此前查明（见[钩爪位移实现](ciyuan_2017/英雄107_钩爪位移实现.md)）：`SBullet.StrScriptFile`
指向 `script/skill/107/bullet*.s`，但**三个安卓包里 `.s` 文件数都是 0**，导致技能/子弹的
行为逻辑无法还原；同时引擎 `CXWindowswLayer::InitEngine` 存在 **Windows 平台分支**
（见[引擎与平台身份](引擎与平台身份.md)）。

**推论**：上述 300大作战 **PC 客户端包**（ZIP）里很可能包含完整的 `script/skill/**/*.s`，
以及 Windows 构建的 Snake 引擎。

**但必须说清边界**：

- 那些是 **300大作战（Jumpw）** 的包，**不是次元大作战**。它们能提供 **`.s` 脚本格式**
  与引擎的 Windows 构建线索，**但不会包含三笠（heroId 107）本人的 `bullet*.s`**——
  不同游戏的角色不同。
- 因此它能回答"`.s` 是什么格式、由谁执行"，**不能直接回答"三笠的钩爪如何判定命中"**。
- 下载的是**商业游戏客户端**，涉及版权；且体积 136 MB ~ 955 MB。

## 四、方法与注意事项

### 4.1 检索命令

```bash
P='http://127.0.0.1:12334'

# 快照是否存在
curl --proxy $P "https://archive.org/wayback/available?url=<域名>"

# 全量 URL 列表（CDX）
curl --proxy $P "https://web.archive.org/cdx/search/cdx?url=<域名>&matchType=domain\
&output=json&collapse=urlkey&limit=500&fl=timestamp,original,statuscode,length"

# 按正则过滤（例如只要压缩包）
... &filter=original:.*(zip|exe|apk).*

# 取原始内容（加 id_ 后缀可跳过 Wayback 的页面注入）
curl --proxy $P "https://web.archive.org/web/<时间戳>id_/http://<原始URL>"
```

### 4.2 注意事项

- **所有请求都必须带 `--proxy http://127.0.0.1:12334`**，否则 archive.org 不可达。
- `id_` 后缀用于取**未被 Wayback 改写**的原始响应；不加则会被注入导航条与脚本。
- CDX 的 `length` 是 **WARC 记录长度**（含头部），不是文件精确大小。
- 大文件用 `Range:` 分段取（实测返回 206），不必整包下载。
- Common Crawl（见下）仍可作为**备用**，其索引与 WARC 分段取回方法已验证可用，无需代理。

## 五、Common Crawl 作为备用通道

`index.commoncrawl.org` / `data.commoncrawl.org` **不需要代理**即可访问。方法：

```bash
curl "https://index.commoncrawl.org/CC-MAIN-<期>-index?url=<域名>&matchType=domain&output=json"
curl -r <offset>-<offset+length-1> "https://data.commoncrawl.org/<filename>" -o rec.warc.gz
# 再 gunzip 得到 WARC 记录（含 HTTP 响应头与正文）
```

已实测取回 `http://download.emagroup.cn/`（2019-01-22，HTTP 200）。

**覆盖面远小于 Wayback**：`emagroup.cn` 在 Common Crawl 里只有 3 个 URL、`ddmoba.com` 无任何抓取。

**踩坑**：WARC 文件名不要手抄——我曾把 `...134236...` 误写成 `...134136...` 导致 `NoSuchKey` 404，
正确做法是从索引响应里直接取 `filename` 字段；Common Crawl 索引连查多次后会返回 502/504，需间隔重试。
